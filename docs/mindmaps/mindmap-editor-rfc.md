# RFC: 在 Kite 中实现独立窗口的工业风 Mindmap 编辑器

- 状态：方向与兼容基线已确认，进入技术验证阶段
- 发起日期：2026-11-26
- 目标：做 macOS 优先、Rust Core 驱动、独立窗口的 XMind 兼容编辑器
- GitHub Discussion：https://github.com/wyz541/Kite/discussions/185
- Feature Issue：https://github.com/wyz541/Kite/issues/186

## 已拍板的产品方向

1. 一个独立编辑器窗口内承载多个文档 tab。
2. `.xmind` 是唯一权威文档格式，不再引入自有的 `.kmind` 用户文件格式。
3. 兼容目标是功能与文件语义的一比一对标，而不是“基础可往返”。
4. 先完成 macOS SwiftUI + AppKit + Rust Core 的端到端实现，再迁移 Windows GPUI。
5. 文本能力不能停在单行标签，必须逐步覆盖 XMind 的换行、富文本和文本编辑体验。
6. 应用默认只提供一套工业风主题，但必须正确读取、保留并最终渲染 XMind 文档自身的主题。
7. v1 不包含云同步、实时协作和账号系统。
8. 一比一基准锁定为当前 XMind 桌面版最新稳定版本；XMind 8 只承担读取和迁移兼容。

## 一句话提案

在 Kite 中增加一个独立窗口的本地优先 XMind 工作台：以 macOS SwiftUI + AppKit 为第一实现，以 Rust Core 作为文档、命令、布局和兼容层，直接打开并保存 `.xmind` 文件。

它不是把 XMind 缩进 Kite，也不是通用白板；它要在不破坏 XMind 文件的前提下，提供一套更快、更键盘友好、更工业化的编辑体验。

## 兼容基线

截至 2026-11-26，XMind 官方 macOS 下载入口解析出的稳定版本为：

- 产品：XMind for macOS
- 版本：`27.01.05089`
- 构建文件名：`Xmind-for-macOS-27.01.05089-202611160640.dmg`
- 服务端最后修改时间：2026-11-17
- 格式基线：现代 `.xmind` ZIP 容器，核心内容以 `content.json` 为主
- 官方下载入口：https://xmind.app/zen/download/mac/

建议在 Slice 0 开始时把实际安装包版本、下载 URL、SHA-256 和样本文件哈希写入兼容性清单。后续如果 XMind 发布新稳定版，应作为显式升级事件处理，而不是静默漂移。

XMind 8 的 `content.xml` 文件只承诺：

- 可以读取。
- 可以迁移为现代 `.xmind`。
- 不承诺在 v1 直接保存回 Legacy 格式。

这样可以把“现代格式的一比一”和“历史格式的迁移”分开验收。

## 这次决策意味着什么

选择 `.xmind` 作为唯一权威格式，并把兼容目标提升到一比一，会让“文件兼容”从一个导入器问题变成产品的主架构约束：

- 未知字段不能丢。
- 未知 ZIP 条目不能丢。
- 不支持的视觉能力至少必须保留并可再次保存。
- 每次保存都必须能证明没有破坏文件语义。
- 主题、布局、富文本和导出不能只做近似效果。
- 兼容性测试需要真实 XMind 文件语料，而不能只靠自己生成的样本。

因此，“一比一”应拆成五个可验收维度：

| 维度 | 含义 | 验收方式 |
|---|---|---|
| 文件安全 | 打开、修改、保存后不丢失未知内容 | 结构化 round-trip 测试 |
| 文件语义 | 已知字段按 XMind 规则读写 | 与 XMind 双向打开验证 |
| 编辑能力 | 支持范围内的功能可完整操作 | 功能矩阵 + 操作录像 |
| 视觉一致性 | 布局、主题、连线、文本接近 XMind | 截图差分和人工验收 |
| 产品体验 | 快捷键、菜单、焦点和错误处理完整 | macOS 真机验收 |

“一比一”不表示复制 XMind 的商标、私有素材、字体或品牌视觉。它是文件互操作和功能对等的目标。

## 为什么放在 Kite

Kite 的核心是导航，不是保管。思维导图也是一种导航：从主题进入分支，从分支进入证据和行动项。

Kite 已经具备三个适合承载它的基础：

- 文件优先：用户先有 `.xmind` 文件，再决定用什么工具打开。
- 本地优先：不需要账号、云端或浏览器运行时。
- 原生窗口：搜索、预览、编辑器、Git、Agent 都已经采用独立窗口模型。

因此，Mindmap 编辑器应作为 Kite 的文件表面存在，而不是另起一个割裂的应用。

## 目标用户与核心任务

### 目标用户

- 已经使用 XMind，但希望获得更快本地编辑体验的 macOS 用户。
- 需要快速整理需求、方案、会议记录和代码结构的开发者。
- 需要把 Markdown 或纯文本转成视觉结构，并能与 XMind 用户交换文件的人。

### 核心任务

1. 直接打开现有 `.xmind`，不先转换、不先复制。
2. 不离开键盘完成新增、改名、移动、折叠和导航。
3. 编辑后仍能被 XMind 正常打开，且不破坏未支持的功能。
4. 导出一张可交付的图，而不是只留下一个应用内结果。

## 先修正“MVP”的含义

如果一比一是最终目标，就不能把“一比一兼容”和“第一个可运行版本”混在一起。

建议把工作分成两个层次：

- **Vertical Slice / 可运行切片**：证明应用能安全打开、编辑和保存一个真实 XMind 文件。
- **Parity Release / 对标发布**：通过完整兼容矩阵，才允许宣称 XMind 对标完成。

任何中间切片都必须满足“文件不被破坏”，但不要求第一切片已经实现全部 XMind 功能。

## 产品范围

### 第一阶段必须完成

- 独立编辑器窗口和多文档 tab。
- 打开、保存、另存为、自动恢复、外部修改检测。
- 多 sheet 文档读取与切换。
- 主题树编辑、键盘编辑、拖拽换父级、折叠、搜索。
- 多行文本、基本富文本和 XMind 主题样式读取。
- 撤销/重做，跨文本编辑和结构操作。
- PNG、SVG 导出。
- XMind 文件安全 round-trip。

### 对标发布需要覆盖

- XMind 的多种结构：思维导图、逻辑图、组织架构图、树形图、时间轴、鱼骨图和矩阵。
- 主题、样式、图标、标签、备注、超链接、图片、附件、关系线、边界和概要。
- 多 sheet、画布定位、缩放和打印/导出流程。
- XMind 快捷键和 macOS 菜单习惯。
- 旧版 `content.xml` 文件读取，或明确提供迁移路径。
- 真实 XMind 文件语料上的双向验证。

### v1 明确不做

- 实时多人协作和评论。
- 云同步、账号体系和移动端。
- 自由画笔、便签墙、无限白板。
- 插件市场。
- 复制 XMind 的商标、私有图标库或品牌素材。
- AI 自动生成导图。可在 Agent 集成稳定后再讨论。

## 设计语言：工业风，不是复古风

这里的“工业风”应理解为：可读、可测、可维护，而不是堆金属纹理或装饰性网格。

建议采用以下视觉约束：

- 窗口外壳使用石墨灰和低饱和中性色，画布保持接近纸张的浅色底。
- 以 1px 规则线、明确对齐、固定栅格和克制的节点圆角建立秩序。
- 选择、焦点、错误和危险操作只使用少量语义色，不使用无意义渐变。
- 状态栏持续显示缩放比例、节点数、保存状态和当前布局。
- 工具栏紧凑，优先图标 + 快捷键提示，而不是大块营销式按钮。
- 文本编辑使用平台原生输入与 IME，不把 canvas 变成文本框。
- 动效只服务于定位和状态变化，不用于装饰。

“Rust 理念”也体现在交互上：

- 状态显式：已保存、未保存、只读、外部修改、恢复中，必须清楚可见。
- 失败可解释：不支持的字段或内容要被识别并保留，不能静默重写。
- 操作可逆：结构编辑、移动和删除都进入统一撤销栈。
- 本地可拥有：文件可读、可备份、可迁移，不依赖服务端。

## 推荐架构

```text
┌──────────────────────────────────────────────┐
│                Mindmap Core (Rust)           │
│ document · command · undo · layout · scene   │
│ xmind container · compatibility · export     │
└──────────────────────┬───────────────────────┘
                       │ typed UniFFI / Core API
          ┌────────────┴────────────┐
          │                         │
 ┌────────▼────────┐       ┌────────▼─────────┐
 │ macOS SwiftUI   │       │ Windows GPUI     │
 │ + AppKit        │       │ later            │
 │ canvas + input  │       │ canvas + input   │
 └─────────────────┘       └──────────────────┘
```

### Core 负责

- 稳定的节点标识和树结构。
- 高层编辑命令及撤销/重做。
- XMind ZIP 容器读取、校验、合并和原子写入。
- 已知 XMind 字段的类型化解析，以及未知字段/条目的原样保留。
- 布局计算和连线路径。
- 富文本与节点尺寸的布局接口。
- 搜索结果和节点定位。
- 导出时使用的平台无关场景描述。

### macOS 外壳负责

- 窗口、多文档 tab、工具栏、菜单、快捷键和焦点。
- 用 SwiftUI Canvas 或 AppKit 自定义视图绘制场景。
- 平台原生文本输入，包括中文 IME、选区和富文本编辑。
- 系统文件选择器、剪贴板、打印和分享能力。
- CoreText 文本测量结果提供给 Rust 布局层。

Core 不暴露 GPUI、SwiftUI 或 AppKit 类型。UI 不复制树结构规则和布局规则。

## XMind 文件策略

### 容器安全

`.xmind` 按 ZIP 容器处理。加载后保留：

- 原始条目路径、字节和压缩信息。
- 已知 JSON/XML 文件的结构化视图。
- 未识别条目和未识别字段。

保存时只重写发生变化的条目。未修改的未知内容必须原样带回。

### 双格式兼容

至少需要识别两类文件：

- XMind Zen/2020+：`content.json` + `metadata.json` + `manifest.json`，可能包含 `resources/`、缩略图和其他条目。
- XMind 8 Legacy：`content.xml` 历史格式。

第一期可以先把现代 `content.json` 做到读写闭环，但必须明确 Legacy 文件是只读、迁移还是完整兼容，不能含糊。

### 无损往返原则

“无损”建议定义为：

1. 打开后不编辑直接保存，不减少任何未知 JSON 字段或 ZIP 条目。
2. 编辑一个节点，不改变其他节点的未知属性。
3. 删除操作只删除用户明确删除的语义对象。
4. 保存失败不覆盖原文件。
5. 兼容测试同时比较 XMind 重新打开后的结构和视觉结果。

### 不做自有 `.kmind`

用户文件只使用 `.xmind`。内部恢复日志可以使用临时文件、journal 或 SQLite，但不得要求用户迁移到一个新格式。

## 文件安全与保存流程

建议采用以下保存事务：

```text
读取原始 ZIP 和 JSON/XML
  → 建立 typed view + opaque preserved view
  → 用户编辑
  → 生成最小 dirty set
  → 写出临时 .xmind
  → ZIP 完整性和 schema 校验
  → 原子替换原文件
  → 记录内容哈希和保存版本
```

必须处理：

- 外部应用同时修改文件。
- 保存中途崩溃。
- 文件只读或无权限。
- 打开的 XMind 版本包含当前编辑器未知的字段。
- 多个 tab 打开同一路径。

## 文本与布局策略

一比一能力意味着文本不能只做单行标签。

建议分三层实现：

1. **文本语义层**：纯文本、换行、段落、基础富文本 run、链接。
2. **测量层**：macOS 先用 CoreText/NSAttributedString 批量测量；Core 负责缓存和失效。
3. **布局层**：Rust Core 计算节点尺寸、换行位置、分支间距和连线锚点。

第一阶段可以先限制富文本编辑入口，但不能把文件中的富文本降级成纯文本再保存。遇到暂不支持编辑的文本格式，应保留原始结构。

## 性能预算草案

以下数字用于讨论，不是发布承诺：

- 1,000 节点文件冷启动到可交互：目标 < 300ms。
- 5,000 节点文件冷启动到可交互：目标 < 1.5s。
- 普通编辑命令到画面更新 p95：< 16ms。
- 平移/缩放在 2,000 可见节点下保持 60fps 级别。
- 强杀进程后最多丢失 500ms 内的编辑；恢复必须可验证。
- 导入失败不产生半写文件；保存失败不破坏原文件。

## 主要技术风险

### 1. 一比一兼容的范围几乎无限

XMind 包含多个结构、主题、富文本、图片、附件、关系线、边界、概要、标记、多 sheet 和历史版本。必须建立版本和功能矩阵，否则“一比一”无法验收。

基准已经锁定为 XMind for macOS `27.01.05089`；仍需用真实语料库把该版本的文件能力和编辑能力逐项枚举。

### 2. 未知字段的保存

只把已知字段反序列化成结构体再写回，会丢失未来字段。必须保留 opaque JSON/XML 子树，或采用可控的 JSON patch。

### 3. 文本测量和富文本

CoreText、SwiftUI 和 XMind 自身的文本布局可能不完全一致。需要建立可重复的文本样例和截图基线，而不是靠肉眼调间距。

### 4. 主题兼容

“默认只有一套工业风主题”是应用默认外观，不等于可以忽略文件里的主题。对于一比一文件兼容，主题数据必须至少被保留；要渲染一致则必须实现 XMind 主题语义。

### 5. 旧版格式

XMind 8 的 `content.xml` 与 Zen/2020+ 的 `content.json` 不是同一种解析路径。需要单独决定读取、迁移和保存策略。

### 6. 大图和增量布局

全量重排 5,000 节点可能阻塞输入。需要把“文档变化”拆成局部失效区域，优先支持增量布局。

## 建议的实现切片

### Slice 0：XMind 兼容性 spike

- 解析一个真实 XMind 文件，包括多 sheet 和样式字段。
- 建立 ZIP manifest、JSON 原文和 typed tree 的对照。
- 打开后不编辑直接保存，验证未知字段/条目未变化。
- 用 macOS SwiftUI/AppKit 绘制 500 节点场景。
- 验证 IME、文本输入、平移、缩放和命中测试。

### Slice 1：安全读写的文档核心

- 建立 `mindmap` Rust 模块。
- XMind 容器、typed/opaque 双层模型、原子保存。
- 节点树命令、撤销栈、恢复日志。
- 兼容性语料和 round-trip 测试。

### Slice 2：macOS 编辑闭环

- 独立窗口、多文档 tab、打开/保存/另存为。
- 键盘编辑、拖拽换父级、折叠、搜索。
- 多行文本、主题读取和基础富文本。

### Slice 3：XMind 能力补齐

- 多结构布局、主题、图标、标签、备注、链接、图片和附件。
- 关系线、边界、概要和导出。
- 双向 XMind 验证和截图差分。

### Slice 4：Windows GPUI

- 先复用 Core 和场景协议。
- 再实现 GPUI 画布、输入覆盖层和 Windows 文件交互。

## 需要继续确认的问题

1. 是否要求第一版就支持全部 XMind 结构类型，还是先以思维导图结构达到完整编辑，再补组织图、时间轴、鱼骨图和矩阵？
2. 是否接受“未支持字段只读保留、后续再补齐编辑”的渐进策略？
3. 是否需要兼容 XMind 的打印、演示和分享流程，还是只覆盖编辑与导出？

## 建议的下一步

先做 Slice 0，不先做完整 UI。这个 spike 应回答三个问题：

- 我们能否在不理解全部字段的情况下安全保存一个真实 `.xmind`？
- macOS 原生文本输入能否和 Rust 布局场景稳定协作？
- 500 到 5,000 节点时，Core 与 SwiftUI/AppKit 的性能是否够用？

如果这三个问题通过，再进入完整编辑器实现；如果文件安全无法证明，不应该开始做大规模 UI。
